# 架构与设计取舍

> 面向技术面试官：这份文档回答"为什么这么拆"，而不是"有哪些文件"（目录结构见 README）。

## 1. 约束条件

- 交付物要能被**零安装打开**（HR/猎头不会装 Python），同时要能被**一行命令重建**（面试官会改数据）。
- 数据必须**可复现**：固定种子重跑得到逐字节一致的结果，否则 README 里的数字第二天就失效。
- 不引入重型框架：一个页面、一份数据、四条命令，引入构建链的收益低于读者理解成本。

## 2. 分层与依赖方向

```
scenario(假设) ──► generate ──► CSV ──► validate ──► metrics/anomalies/insights ──► pipeline ──► metrics.json ──► render ──► index.html
```

| 层 | 职责 | 依赖 | 是否纯函数 |
| --- | --- | --- | --- |
| `scenario.py` | 平台体量、品类结构、促销日历、退款基线、注入异常 | 无 | — |
| `generate.py` | 把假设展开成三张事实/维表 | numpy | 是（显式传入 `rng` 与日期区间） |
| `validate.py` | 列/类型/非空校验、履约订单守恒 | pandas | 是 |
| `metrics.py` | 口径唯一实现（聚合与比率） | pandas | 是 |
| `anomalies.py` | 异常检测 | pandas | 是 |
| `insights.py` | 结论生成 | pandas | 是 |
| `pipeline.py` | 编排、合并、落盘 | 上述 + 文件系统 | 否（I/O 边界） |
| `render.py` | 模板替换与自包含构建 | 文件系统 | 否（I/O 边界） |

依赖只向下：计算层不知道文件在哪，因此测试不需要造目录、也不用 mock 文件系统。

## 3. 关键决策

### 3.1 为什么拆成两张事实表，而不是一张宽表

销售事实的粒度是「日期 × 平台 × 品类 × 渠道」，履约事实是「日期 × 平台 × 品类 × 时效分桶」。
合并成宽表会出现笛卡尔积：5 个渠道 × 5 个分桶 = 25 行，订单数被放大 5 倍。
拆开后各自聚合、再在指标层按平台/月份对齐，订单数守恒（生成时用 `rng.multinomial`
保证分桶之和等于该组订单数，并有单测与 CI 校验）。

### 3.2 为什么口径只写一遍

`metrics.py` 是 GMV/AOV/CVR/退款率/48h 达成率的**唯一实现**；README 的口径表、Power BI 的 DAX、
FineBI 的计算字段都引用它。代价是固定了指标命名与计算路径，收益是"文档与代码永远不会漂移"。

被拒绝的方案：在 SQL / DAX / Python 各写一份"看起来一样"的公式。三份实现必然在边界条件上分叉
（除零、退款归因日、分桶加权），而这正是本项目要解决的问题本身。

### 3.3 为什么异常检测用"前 3 个月中位数 + 双阈值"

- 固定阈值（如退款率 > 20%）：平台基线和品类结构不同，会大量误报。
- 均值 + 标准差：大促单月尖峰会把均值与标准差一起抬高，掩盖异常。
- 中位数基线 + `≥2.5pp` 且 `≥18% 相对抬升`：绝对阈值过滤小基数噪声，相对阈值过滤"高基线品类的正常波动"。

局限：对"缓慢持续上升"不敏感（基线会跟着抬升）。如果要上生产，应换成 STL 分解或同比基线，
并补一条回归测试。这是刻意保留的简化，写进 README 的已知限制。

### 3.4 为什么同比用"去年同月"而不是"前半段 vs 后半段"

20 个月数据里，按"前 14 个月 vs 后 6 个月"切分会把 618/双11 的分布差异当成增长（曾得到抖音 -50.9% 的错误结论）。
改为"最新完整月 vs 去年同月"后为 +27.7%。这也解释了为什么 `pipeline.py` 在不足 13 个完整月时**直接报错**：
宁可拒绝运行，也不输出一个季节性失真的同比。

### 3.5 为什么构建成单文件

把 ECharts（约 1MB）与 `metrics.json` 内联进 `index.html`：

- 读者双击即可打开，`file://` 协议下没有跨域/资源 404 问题；
- 可以直接部署到 GitHub Pages / 内网静态服务器，无需构建；
- 代价是 1.3MB 产物入库，且每次数据变化都会产生一个大 diff（用 `data/metrics.json` 做 review 更有意义）。

被拒绝的方案：`<script src="cdn...">`（离线/内网打不开）、Vite 打包（为一个页面引入构建链）。

### 3.6 为什么参数外置但不引入 pydantic / dotenv

运行参数只有 6 个，标准库 + 20 行 `.env` 解析即可，且不新增依赖。
校验集中在 `load_settings()`：日期先后、日志级别、路径解析一次做完，避免错误在下游以 `KeyError` 形式出现。

## 4. 失败模式与可观测性

| 失败 | 表现 | 处理 |
| --- | --- | --- |
| CSV 被替换/缺列 | `DataContractError` | CLI 退出码 2，打印缺哪一列 |
| 周期不足 13 个月 | `DataContractError` | 提示调整 `KPI_START_DATE` |
| 履约与销售订单不守恒 | 告警 >0.1% | `WARNING` 日志，不中断（外部数据可能有舍入） |
| 模板占位符被删 | `DataContractError` | 明确指出缺 `__DATA_JSON__` 还是 `__ECHARTS__` |
| 未预期异常 | 完整 traceback | 退出码 1，便于区分"环境问题"与"代码缺陷" |

日志分级约定见 `logging_setup.py`：`INFO` 只讲产物与规模，`WARNING` 讲数据可疑，`DEBUG` 讲细节。

## 5. 如何接入真实数据（扩展点）

保留 `metrics.py` 及下游不动，替换 `generate.py` 的输入层即可：

1. 新增 `ingest.py`，把平台报表导出映射成 `SALES_COLUMNS` / `FULFILLMENT_COLUMNS`；
2. 在 `pipeline.run_metrics` 中把"读 CSV"换成"读 ingest 结果"；
3. `validate_frame` 继续作为边界校验，列契约就是接口。

刻意**没有**做的抽象：DataLoader 接口、插件注册表、配置类继承体系。
只有一组数据源时这些抽象没有收益；真正做到多数据源时再引入，成本更低。

## 6. 测试与 CI 策略

| 测试 | 覆盖点 | 为什么值得测 |
| --- | --- | --- |
| `test_metrics.py` | 比率由分子分母重算、分桶加权 | 口径错了，所有结论都错 |
| `test_anomalies.py` | 命中尖峰、忽略普涨、双阈值边界、排序截断 | 规则最容易在调参时被破坏 |
| `test_generate.py` | 同种子一致、异种子不同、履约订单守恒、促销峰值、日历标记 | 可复现性与事实表一致性 |
| `test_pipeline.py` | JSON 结构、促销窗口合并、周期不足报错 | 看板契约（前端依赖字段名） |
| `test_render.py` | 占位符替换、缺文件/缺占位符显式失败 | 单文件构建是最大卖点，不能静默坏掉 |

CI 额外做两件单测覆盖不到的事：**重建产物逐字节比对**（证明可复现）、**单文件自包含校验**（占位符已替换、体积、内联数据存在）。
